# API contract
Audience: engineers · Last updated: 2026-11-14 by UGcraftist
Sources: DR-0002 (REST), DR-0004 (stack), DR-0005 (Supabase/PostgREST, amended), DR-0006 (SQL-editor migrations),
ux.md (screens), requirements.md FR-001…FR-022, supabase/migrations/0002_read_model.sql

The backend **is PostgREST** over Supabase (DR-0005): there is no hand-written server and no
`api/` folder. Tables, views and RPC functions in `public` are the HTTP surface under
`https://<project>.supabase.co/rest/v1/`. The OpenAPI document is **generated by PostgREST**
(GET `/rest/v1/`) — it is not committed, because PostgREST's own copy is the truth for filters,
operators and error shapes.

## Conventions

- **Auth**: writers send `Authorization: Bearer <editor JWT>` (Supabase Auth); RLS policies decide.
  R1 requires login (editor metadata `role=editor`, DR-0005). Anonymous read arrives with the
  public share in T-015.
- **Reads**: `GET /rest/v1/<table|view>?select=...` with PostgREST filters
  (`id=eq.`, `name=ilike.`, `order=`, `limit=`, `offset=`) and `Range` headers for pagination.
- **Writes**: through RPC functions (`POST /rest/v1/rpc/<fn>`), never raw multi-row POSTs — the
  functions own validation, status transitions and audit triggers (T-007).
- **Errors**: PostgREST JSON `{"code","details","hint","message"}`; HTTP status is the contract
  (400/401/403/404/409/422).
- **Time**: visible dates are returned as `*_date` (`YYYY-MM-DD`) + `*_precision`
  (`day|month|year|unknown`); the frontend's `format()` renders the text (FR-014).
- **Rows are append-only for facts**: a revision is a new row whose `revision_of` points at the
  old one; the old row becomes `superseded` (US-021). PATCH is not part of the contract for facts.
- **Versioning**: PostgREST views are versioned by migration (`0002_read_model`, …); breaking
  shape changes go through a new DR (DR-0002).

## Write surface (Must, T-007 · migration `write_rpc`，编号见 data-model.md 迁移台账)

| Call | Purpose |
|---|---|
| `POST rpc/upsert_fact` | create a draft or a revision (`revision_of`); payload may nest `sources[]`, written in the same transaction and deduped by normalized URL |
| `POST rpc/submit_fact` | draft → published (R1 collapses `in_review`, FR-031 is R2; no separate `publish_fact` — T-007 decided not to split); refuses a publish without a source or `no_source`, supersedes the old revision, writes one audit row |
| `POST rpc/upsert_stance` | stance upsert (R1 test set stays empty) |
| `POST rpc/merge_source` | dedupe sources by URL and re-link facts (destructive) |
写路径按注册表执行两端规则：`subject_kinds` 空 = 任意；`object_kinds` 空 = 不得带 object，非空 = 必须带且种类在列内（`data-model.md` 注册表一节）。

R1 折叠 `in_review`：`submit_fact` 直接发布（FR-031 的 editor→reviewer 流程属 R2）。
`audit_log.summary` 记 `from_status`/`to_status`，R2 恢复状态机时读回即可。

### `merge_source` URL normalization (destructive, one-way)

`merge_source(p_from, p_into)` 仅在两个来源的**归一化 URL 完全相同**时视为重复（T-007 实现并测试）：

- 去首尾空白；
- scheme 与 host 转小写，路径与查询串保留原大小写；
- 去掉 fragment（`#...`）；
- 去掉默认端口（`http:80`、`https:443`）；
- 路径为空时去掉末尾 `/`。

合并会删除重复来源并把其 fact 重新挂到保留来源上，**不可逆**；T-007 必须同时给出正例
（归一化后相同 → 合并）与负例（路径不同 → 拒绝，不删行）。

## Response snippets (0002/0005 read model)

```json
// GET /rest/v1/tree_nodes
[{"id":"0191…","name":"Agile Robots","kind":"company","country_code":"DE",
  "founded_date":"2018-01-01","founded_precision":"year",
  "depth":0,"is_root":true,"child_count":1,"parent_count":0}]

// GET /rest/v1/org_detail?id=eq.0191…  (shape changed by 0005: both fact ends)
[{"id":"0191…","name":"Boston Dynamics","kind":"company","country_code":"US",
  "founded_date":"1992-01-01","founded_precision":"year","notes":null,
  "facts":[{"id":"0192…","predicate":"split_from","label_zh":"拆分自","label_en":"split from",
            "status":"published",
            "conflict_key":"3f0c…",
            "subject_kind":"org","subject_id":"0191…","subject_name":"Boston Dynamics",
            "object_kind":"org","object_id":"0193…","object_name":"MIT",
            "start_date":"1992-01-01","start_precision":"year",
            "end_date":null,"end_precision":null,"qualifier":"exact","amount":null,
            "certainty":"exact","no_source":false,
            "sources":[{"title":"…","url":"https://…","kind":"article","quote":"…",
                        "locator":null,"author":"…","page":null,
                        "published_at":"2026-01-01","accessed_at":"2026-11-19T00:00:00Z"}]}]}]
```

`org_detail` resolves **both** ends of each fact server-side: `subject_kind/id/name` and
`object_kind/id/name`. It emits `published` **and** `disputed` facts with an opaque
`conflict_key` (md5 of the raw oriented triple, computed before the visibility gate — never
recompute it from the returned ids, which are nulled for hidden counterparts). Clients group on
`conflict_key`; PostgREST cannot group server-side. `published_at` (出版) and `accessed_at` (访问)
are distinct; the drawer never presents one as the other. The `*_id` and `*_name` of an end are `null` when that end is not
`visibility='public'` (security.md:33); a fact with no object end (e.g. `founded`) has
`object_kind = null`. Clients must render the subject end first; fact ends must not be resolved from `tree_nodes`
(that map is tree-only and misses persons and gated orgs), though it may still label the drawer title.

`facts_for(uuid)` is the single fact-shaping function both `org_detail` and the future person view
call; it is exposed at `POST /rest/v1/rpc/facts_for` to `authenticated` and `service_role` only (documented here because
it is reachable). **R1 known limitation:** `tree_edges` still filters `status='published'`, so a
disputed relation appears in the detail drawer but not on the canvas; the provenance chip (ux.md)
lands with T-011/T-012. **Fixture limitation:** every seeded conflict end is public, so a `conflict_key`
computed *after* the visibility gate would still group the seeded pair — the pre-gate property is
asserted by construction in 0008 and needs a hidden-counterpart fact (T-024's person data) to be
demonstrated end-to-end.

## Coverage

Every Must story maps to a read or write call above. US-012 filters are HTTP parameters on
`tree_edges`/`orgs`; US-002/US-009 conflict groups are derived client-side from the opaque
`conflict_key` that migration `detail_contract` adds to `org_detail` (PostgREST cannot group rows
server-side; T-010); US-015 (URL state) is purely frontend.
