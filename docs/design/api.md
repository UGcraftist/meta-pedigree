# API contract
Audience: engineers · Last updated: 2026-11-14 by UGcraftist
Sources: DR-0002 (REST), DR-0004 (stack), DR-0005 (Supabase/PostgREST, amended), DR-0006 (SQL-editor migrations),
ux.md (screens), requirements.md FR-001…FR-022, supabase/migrations/0002_read_model.sql

The backend **is PostgREST** over Supabase (DR-0005): there is no hand-written server and no
`api/` folder. Tables, views and RPC functions in `public` are the HTTP surface under
`https://<project>.supabase.co/rest/v1/`. The OpenAPI document is **generated by PostgREST**
(GET `/rest/v1/`) — it is not committed, because PostgREST's own copy is the truth for filters,
operators and error shapes.

## Conventions

- **Auth**: writers send `Authorization: Bearer <editor JWT>` (Supabase Auth); RLS policies decide.
  R1 requires login (editor metadata `role=editor`, DR-0005). Anonymous read arrives with the
  public share in T-015.
- **Reads**: `GET /rest/v1/<table|view>?select=...` with PostgREST filters
  (`id=eq.`, `name=ilike.`, `order=`, `limit=`, `offset=`) and `Range` headers for pagination.
- **Writes**: through RPC functions (`POST /rest/v1/rpc/<fn>`), never raw multi-row POSTs — the
  functions own validation, status transitions and audit triggers (T-007).
- **Errors**: PostgREST JSON `{"code","details","hint","message"}`; HTTP status is the contract
  (400/401/403/404/409/422).
- **Time**: visible dates are returned as `*_date` (`YYYY-MM-DD`) + `*_precision`
  (`day|month|year|unknown`); the frontend's `format()` renders the text (FR-014).
- **Rows are append-only for facts**: a revision is a new row whose `revision_of` points at the
  old one; the old row becomes `superseded` (US-021). PATCH is not part of the contract for facts.
- **Versioning**: PostgREST views are versioned by migration (`0002_read_model`, …); breaking
  shape changes go through a new DR (DR-0002).

## Read surface (Must)

| Call | Purpose | Story |
|---|---|---|
| `GET tree_nodes?order=depth.asc,name.asc` | whole pedigree skeleton: name, country, founded, depth, root flag, child/parent counts | US-004 |
| `GET tree_edges?parent_org_id=eq.<id>` | children of one node for expand/collapse + relation type/date | US-004, US-012 |
| `GET org_detail?id=eq.<id>` | org row + published facts with sources as JSON (detail panel) | US-001, US-002, US-004, US-008 |
| `GET orgs?name=ilike.*q*&kind=eq.company` | name search and facet filter (until T-013 adds `search_orgs`) | US-005, US-008, US-014 |
| `GET facts?id=eq.<id>` | fact detail: sources are embedded by the RPC/view layer in T-007; R1 detail uses `org_detail` | US-001, US-002, US-006, US-009 |
| `GET sources?select=*&id=in.(...)` / `fact_sources` | source list per fact, source CRUD backing | US-001 |
| `GET relation_types` / `GET stance_axes` | controlled vocabulary (registry) | US-024 |
| `GET stances?party_org_id=eq.<id>` | party stances incl. to-China / to-US axes (R1 returns empty) | US-024 |
| `GET audit_log?entity=eq.fact&entity_id=eq.<id>` | editor-only audit trail | US-021 |
| `GET timeline_events?order=start_date` | timeline view (view lands with T-009) | US-010 |

## Write surface (Must, T-007 · migration 0003_write_rpc)

| Call | Purpose |
|---|---|
| `POST rpc/upsert_fact` | create a draft or a revision (`revision_of`), validate date/precision pairing |
| `POST rpc/submit_fact` | draft → in_review → published; refuses published facts without a source |
| `POST rpc/upsert_stance` | stance upsert (R1 test set stays empty) |
| `POST rpc/merge_source` | dedupe sources by URL and re-link facts |
| `POST rpc/publish_fact` (if split out) | publish step for S-10 (exact split decided in T-007) |

## Coverage

Every Must story maps to a read or write call above. US-012 filters are HTTP parameters on
`tree_edges`/`orgs`; US-013 conflict groups arrive with the facts view in T-007; US-015 (URL state)
is purely frontend.
